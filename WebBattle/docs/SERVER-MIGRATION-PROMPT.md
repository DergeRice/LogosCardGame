## 목적과 반드시 지킬 조건

이전 이유는 Cloudflare 무료 DB의 일일 쓰기 한도 때문에 집계뿐 아니라 게임 전체가 중단된 것이다. 진단/문장 집계가 중단되더라도 방 생성·입장·매칭·경기·보상 저장이 계속되어야 한다. 네트워크 장애나 서버 용량 초과까지 ‘무조건 방 생성 가능’이라고 보장하지는 마라.

1. Netlify와 기존 R2 음원 서비스는 유지하고 게임 실행·필수 데이터 저장을 Cloudflare Durable Objects 한도에서 분리해라. Node 장기 실행과 WebSocket, 영구 저장소가 가능한 환경을 사용해라. 현재 계정에 쓸 수 있는 서버가 있는지 먼저 확인해라. 사용량 기반 무제한 과금으로 문제를 덮지 마라.
2. 처음에는 단일 권위 게임 프로세스로 일관성을 유지해라. 영구 디스크 SQLite 또는 사용 가능한 PostgreSQL을 선택하고 근거를 기록해라. 휘발성 디스크, 자동 휴면 때문에 진행 중 경기가 사라지는 구성, 조정 없이 프로세스/인스턴스를 여러 개 띄우는 구성은 사용하지 마라. 다른 프로세스에서 재접속하면 다른 메모리 방에 들어가는 문제를 막아라.
3. 기존 계정·비밀번호 해시/솔트·Apple 식별자·인증 세션·게스트 식별자·친구·초대·보유 아이템·장착·포인트·골드·레이팅과 랭킹 기록을 보존해라. 경기 복구용 카드 순서·손패·필드·점수·고 상태·타이머·중복 요청 식별자도 보존해라. 운영 데이터를 테스트 데이터로 덮어쓰지 마라.
4. 게임 상태 변경과 영구 커밋을 순서대로 처리하고, 성공 응답/방송은 필수 커밋 이후에 보내라. 서버 재시작·재접속·중복 요청에서도 카드 복제, 점수 중복, 보상 이중 지급이 없어야 한다. 실제 필수 DB 저장 실패를 성공으로 위장하지 말고 명확한 오류와 복구 경로를 제공해라.
5. 진단·통계는 필수 상태 저장과 별도 실패 경계에 두어라. 집계 예산 초과·큐 포화·외부 집계 서버 다운·타임아웃·로그 저장 예외가 게임 커밋을 취소하거나 서버를 abort하지 않아야 한다. 큐와 메모리는 크기를 제한하고 오래 기다리지 말고 집계만 버려라. 일반 요청·UI 조작·AI 상세 로그는 저장하지 않는 현재 정책을 유지해라. 사람 제출/오류에 적용한 하루 1,000건 제한과 오류 중복 억제도 유지하되 정확한 집계 범위를 README에 기록해라.
6. 기존 클라이언트 프로토콜과 현재 경기 규칙을 유지해라. 최소 4명까지 AI 충원, 최대 6인, AI 난이도, Rob/Protect/Exchange, 고 선택/승패/재화 정산, 덱 소진 및 기본 카드 공급 등을 현재 코드와 테스트 기준으로 검증해라. 이 이전을 이유로 규칙이나 TTS 동작을 다시 설계하지 마라.
7. `/health`는 필수 저장이나 집계 쓰기를 하지 않아야 한다. 상태 확인·로그 조회·관리자 메모·접속 제어·재화 지급 등 기존 API도 조사해서 필요한 기능을 옮겨라. 읽기 공개 범위와 관리자 쓰기 인증을 임의로 넓히지 마라. Origin, WSS/TLS, 역방향 프록시의 IP 신뢰 범위, 메시지/접속 제한, 비밀 환경 변수를 확인해라. 서버 비밀키를 Vite 번들에 넣지 마라.

## 데이터 이관과 운영 전환

- 실제 원본 데이터 구조와 내보내기 경로를 조사해라. 현재 공개 문장/로그 API는 전체 계정·세션·게임 상태 백업 수단이 아니다. 필요하면 인증된 임시 읽기 전용 export 경로를 구현하고 작업 후 정리해라.
- Cloudflare 한도로 접근 불가하면 한도 초기화 뒤 백업을 확보해라. 빈 DB로 시작하거나 임의 데이터로 복원하지 마라. 접근 불가 상태를 숨기지 마라.
- 원본 백업, 이관 도구, 스키마 버전, dry-run, 재실행 안전성, 키별/종류별 개수 및 주요 잔액 대조, 복원 검증을 준비해라. 개인정보·인증 토큰·비밀번호 해시가 든 덤프와 비밀키는 Git에 올리거나 도구 출력으로 노출하지 마라.
- 진행 중 방과 신규 접속을 어떻게 처리할지 정해라. 두 서버가 같은 계정의 재화·레이팅을 동시에 갱신하는 split-brain을 막아라. 최종 백업/이관 때 이전 서버 쓰기를 중지하거나 명시적인 전환 창을 두어라.
- 새 서버를 먼저 검증한 뒤 Netlify `VITE_WS_URL`과 관리자 API 주소를 전환해라. Apple 로그인 리다이렉트·자격 증명과 기존 세션 재사용을 확인해라.
- 롤백은 단순히 URL만 되돌리는 절차로 끝내지 마라. 새 서버에서 변경된 계정/보상/경기 진행을 보존하고, 어느 서버가 권위 원본인지 정한 뒤 되돌려라. 기존 서버/데이터는 안정화와 백업 검증 전까지 삭제하지 마라.

## 검증과 완료 조건

- 로컬 및 실제 새 런타임에서 방 생성·입장·매칭, 4인/6인 경기, 재접속, 프로세스 재시작 복구, 계정 로그인과 정산 중복 방지를 검증해라.
- Cloudflare 집계가 요청을 거절하거나 다운된 조건을 주입하고도 새 방 생성·경기·필수 저장·결과 정산이 성공하는지 검증해라. 집계 장애가 조용히 게임 상태 손실로 이어져서는 안 된다.
- 중복 제출·타이머 만료·동시 요청·서버 종료 중 커밋 같은 장애 조건을 확인해라. 프록시를 거친 실제 WSS 연결과 기존 모바일 클라이언트 호환성도 확인하고 실제 기기와 에뮬레이션 결과를 구분해라.
- 적절한 부하 시험으로 해당 서버의 동시 방/연결 여유를 측정해라. 수용량을 넘으면 기존 경기를 손상시키지 않고 신규 요청에 재시도 안내를 제공해라. 단일 서버 장애와 디스크 장애의 한계, 백업/복구 방법도 기록해라.
- README에 로컬 실행·배포·환경 변수·백업/복구·전환/롤백 절차와 비용 구조를 남겨라. 현재 제공업체 가격은 실행 시 공식 자료로 확인하고 추정치와 구분해라.
- 새 유료 서비스 생성·결제·요금제 변경이 필요하면 구체적인 선택안과 월 예상비, 추가 과금 조건을 정리하고 사용자 승인을 받아라. 그 전에 가능한 코드·테스트·설정·이관 준비는 끝내라. 기존의 이미 승인된 환경에서 가능한 작업에 불필요하게 재확인을 요구하지 마라.
- 실제 운영 전환을 검증한 경우에만 ‘이전 완료’라고 보고해라. 접근 권한/호스팅 승인이 없어 전환하지 못했다면 준비 완료 범위와 남은 단계를 명확히 구분해라.
- 구현 변경은 AGENTS.md의 버전 규칙을 따르고, 작업 완료 시 Git 커밋과 `web-battle` 푸시, Netlify 배포 확인을 진행해라. 이전 후에는 실제 사용하는 새 게임 서버를 배포·검증하며 불필요하게 구 서버를 다시 활성화하지 마라.
